A Kastor module is a directory tree of `.agent`, `.tool`, `.prompt`, and project files. Files reference blocks by address, not by path.

```text
agent.weather
tool.web_search
prompt.weather_system
model.fast
target.langgraph
```

## Agents

An agent owns its model, tools, optional system prompt, input contract, output contract, and dependency hints.

```hcl
agent "weather" {
  model         = model.fast
  system_prompt = prompt.weather_system
  tools             = [tool.web_search]
  requires_approval = [tool.web_search]

  input "location" {
    type = string
  }

  output "weather" {
    type = string
  }
}
```

The current type set is intentionally small: `string`, `number`, and `bool`.

`tools` is the agent's grant. A tool omitted there cannot be called;
`requires_approval` narrows granted tools by pausing their calls for a human.
The two lists are not peers, so an approval entry that is absent from `tools`
is an error rather than an implicit grant. Tools in `tools` but not in
`requires_approval` run unsupervised.

## Tools

A tool is an interface plus an implementation source.

```hcl
tool "web_search" {
  description = "Search the web"

  param "query" {
    type = string
  }

  returns {
    type = string
  }

  source {
    kind = "mcp"
    uri  = "mcp://search-server/tavily_search"
  }
}
```

Implemented parser support includes `mcp`, `http`, `builtin`, `runtime`, and `script` source kinds. What a kind means is the target's decision: LangGraph and eve codegen support `mcp`, `http`, and `runtime`, while the `claude_agents` platform supports `mcp` and `builtin`. `script` glue is deferred everywhere. See the [source kinds table](/reference/language#tool) for the full matrix.

## Prompts

A prompt is frontmatter plus a raw template body.

```text
---
name     = "weather_system"
requires = ["location"]
---
You are a weather assistant. The user is asking about {{location}}.
```

Prompts do not own models or IO. Agents own those. Kastor checks that prompt variables can be satisfied by the agent using the prompt.

## Project config

Current project files are named `kastor.hcl` or use the `.kastor` extension.

```hcl
model "fast" {
  provider = "openai"
  id       = "gpt-4o-mini"

  params {
    temperature = 0.2
    max_tokens  = 4096
  }
}

target "langgraph" {
  type   = "codegen"
  output = "./gen/langgraph"
}

target "memory" {
  type = "platform"
}
```

`adl.hcl` appears in some early wording around the project, but it is not an implemented project filename in the current parser.

## References and dependency inference

References create validation edges and dependency edges.

```hcl
input "forecast_context" {
  type    = string
  default = agent.forecast.output.summary
}
```

That reference means:

- `agent.forecast` must exist
- `agent.forecast` must declare `output "summary"`
- `agent.weather` depends on `agent.forecast`

In v0 codegen, cross-agent references order and validate the graph. They do not automatically run the upstream agent and pass data. The caller still provides the input value.

Use `depends_on` when you need ordering without data flow:

```hcl
depends_on = [agent.geocoder]
```

Cycles are validation errors.

## State

For platform targets, Kastor stores local state in `kastor.state.json` at the module root.

State maps block addresses to remote IDs and the last-applied config:

```json
{
  "version": 2,
  "serial": 1,
  "targets": {
    "memory": {
      "plugin": {
        "source": "builtin/memory",
        "version": "builtin",
        "protocol": 0
      },
      "resources": {
        "agent.weather": {
          "id": "mem-3",
          "config": {}
        }
      }
    }
  }
}
```

The resource unit is currently the agent. Models, prompts, and tools are folded into the agent config for platform reconciliation.

Do not commit `kastor.state.json`. It is environment-specific.

### Plugin ownership and migration

State v2 records each platform target's canonical plugin source and resolved
version/protocol. A supported version upgrade or local plugin alias rename for
the same source does not change ownership. Kastor rejects a different source
while resources remain managed. Destroy with the original owner before
switching sources.

Kastor reads v1 state in memory using your explicit `target.plugin` and
`required_plugins` declarations. Keep the original target labels. A managed v1
Claude target named `claude_agents` must select
`github.com/getkastordev/kastor-anthropic`; missing declarations are errors.
Other v1 labels rely on your declaration of the original source because v1 did
not record it. The built-in `memory` target needs no plugin declaration and
records `builtin/memory`. Its remote objects remain ephemeral.

Back up the state, module files, and plugin lock before migrating; Kastor does
not create an automatic backup. Plan and doctor never persist a migration.
Apply writes v2 with each successful state mutation, or once after a successful
no-op apply. Destroy writes after each successful deletion. A format upgrade
alone causes no remote changes, and preserves IDs, dependencies, and equivalent
last-applied configs. All managed targets need ownership declarations, even
when you select just one with `--target`.

After a partial failure, keep the newest state and retry after fixing the
failure. Do not restore a pre-migration backup over completed remote operations.
Older v1-only binaries cannot read v2; only restore the old state and matching
module/lock if no remote changes have occurred since the backup. Unknown future
formats are rejected rather than rewritten.
